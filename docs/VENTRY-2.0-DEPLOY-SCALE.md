# Ventry 2.0 — P1: безопасная поставка и масштабирование

## Поставка

Старый entrypoint копировал новый сайт поверх действующего каталога до проверки и перезапуска. Кандидат сохраняет неизменяемые каталоги в /opt/ventry/releases, сериализует поставки через flock, проверяет архив (SHA-256 для каждого файла, ограничения размеров, запрет ссылок, специальных файлов, дубликатов и неожиданных путей), проверяет текущий релиз, фиксирует старый Docker-образ и собирает новый отдельно.

При активации используется тот же Compose-проект ventry и постоянные тома. Проверяются TLS без отключения валидации, /healthz, точные version.json и index.html через localhost. Указатель current переключается только после успешных проверок. При ошибке активации выполняется попытка вернуть предыдущую конфигурацию и образ с повторной проверкой; ошибка отката явно сигнализируется. Внешний smoke-test GitHub Actions по-прежнему проверяет все поставленные файлы.

**Перед merge:** администратор должен отдельно проверить на стенде успешную активацию и принудительный отказ, затем установить новый проверенный restricted entrypoint в /usr/local/sbin/ventry-github-status (сохранить исходный файл и права). CI проверяет VENTRY_STAGED_DEPLOY_V1 до отправки архива. Старый entrypoint не сможет выполнить новую поставку. Само изменение репозитория не обновляет сервер.

Не меняются .env, данные других проектов, DNS и постоянные тома. Релизы/образы не удаляются автоматически; контроль свободного места и политика очистки — отдельная задача. Возможен кратковременный простой при пересоздании контейнера. Откат при SIGKILL, аварии питания, повреждении Docker или сбое внешней проверки после успешной локальной активации не гарантируется. Манифест обеспечивает целостность, а не независимую криптографическую подпись релиза; транспорт доверенный SSH. Первоначальная поставка требует проверяемую уже запущенную версию.

## Производительность

История операций отображается страницами по 100 строк, фильтры сбрасывают страницу, переход к операции демо учитывает её страницу. CSV остаётся полным. Выписка конкретного клиента для печати сохраняет все записи.

Проверка Node.js 22.16.0: 100 000 операций, 1000 клиентов, 50 000 оплат, 1000 страниц. Остатки, просрочки, фильтр, JSON round trip, отказ при переплате, дубликате, превышении лимита и отсутствие потерь при пагинации: 3/3 PASS. Замеры одного локального прогона: validation 223 ms, overview 52 ms, history 24 ms; JSON 12 228 707 байт. Git blob ledger e836893051a3f891409d508e58b2c7d99d90d1c6, history 3378cfc66c7d22900d1d4cf674e0a96f7fe7cc1c, tests e25cc95eac5312a69ecae3c4ff33b3143c21d9e7 совпали с файлами ветки.

Верификатор архива: 7/7 PASS локально на идентичном извлечённом Python-блоке (2240 символов, FNV-1a 5ec5ec5c), тестовый файл Git blob 022e3113c374c6c1dfe62992a9359ed5b42d009c совпадает с веткой. Проверены валидный пакет, повреждение файла, пропущенный файл, traversal, дубликат, неожиданный корень и неучтённый файл.

**Ограничение:** тест ядра в памяти не доказывает хранение 100 000 операций в localStorage; размер тестового JSON уже превышает типичную квоту. Следующий этап — транзакционное хранилище IndexedDB, безопасная миграция существующего JSON без удаления источника, реальные браузерные тесты. Не заявлять поддержку 100 000 записей в production до этой проверки.

Docker, полный shell entrypoint, Chromium, Actions и VDS: NOT RUN/не подтверждены на текущем кандидате. Локальное клонирование не работает из-за DNS; Docker в локальном окружении недоступен.
