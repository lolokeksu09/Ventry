# Cloud backup staging contract (Issue #89)

Phase 1: SQL migration 007 and opt-in Rust storage boundary. Not yet mounted into fresh Compose, applied to production, or allowed through private/public Caddy. DELIVERY_BACKUP_ENABLED=true requires migration; default false. Existing licenses, release metadata and customer rows unchanged.

Authorization uses existing refresh secret and installation UUID, with current binding revision checked inside the same SQL transaction as the operation. Subscription owns its slots; authorized device transfer preserves ciphertext. No caller-supplied subscription ID. Read/list after expiry for the still-bound device; upload requires active trial/paid entitlement. Existing server policy for reactivation on a replacement device after expiry remains unchanged and is a rollout decision, not a guarantee of lifetime recovery.

POST /api/v1/backups/list (empty body); /api/v1/backups/{slot}/read (empty body, X-Ventry-Backup-Version UUID); /api/v1/backups/{slot}/put (application/octet-stream, X-Ventry-Backup-Version UUID and X-Ventry-Backup-Expected empty or previous UUID). All require Authorization Bearer existing refresh secret and X-Ventry-Installation UUID. Responses list metadata or raw bytes with SHA256. Three explicit slots, 16 MiB per encrypted envelope (48 MiB maximum current ciphertext per subscription). No automatic eviction, no background overwrite, no deletion endpoint in this phase. Explicit CAS replacement overwrites chosen slot; stale writes conflict; retry of the currently stored version with identical bytes returns same metadata. A stale historical version cannot overwrite a newer slot with its old expected UUID. No per-customer plaintext data, names or debt rows. PostgreSQL/WAL/backups may use additional storage; capacity and retention policy must be approved before production. Global fixed budget 60 requests/minute and four admitted backup requests, independent of activation, response bytes hold the permit while being sent; external edge body/time/concurrency limits still required. Synthetic tests only; no real user data.

VRB1 proposed wire format: ASCII magic VRB1 (4), random salt (16), random nonce (12), AES-256-GCM ciphertext/tag (16-byte tag), header as AAD. PBKDF2-HMAC-SHA256 600000 iterations, UTF-8 recovery passphrase with explicitly documented normalization. Minimum 49 bytes. Client phase must implement and test actual encryption, entropy, cross-device recovery, bounded decryption, wrong key/tamper rejection and existing v5 book validation before atomic restore. Server checks format/size, not proof of encryption; never send recovery passphrase or decrypted book to server. No universal server recovery key. Owner's decision needed for retention/deletion, expiry recovery on new device and commercial quota before launch.
