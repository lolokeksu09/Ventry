# Ventry Delivery — этап 2/3: закрытый Rust API и выдача проверенного APK

Система разработана для изолированного staging, не развёрнута на production. Сайт Ventry, Caddy, Compose, текущая база и Android не изменены. Тарифы и финансовая логика берутся из этапа 1.

## Состав и модель угроз

- `delivery/service/`: Axum/Rust, PostgreSQL, два разных loopback-слушателя, защищённый операторский интерфейс на HTML/CSS/JS. Администратор имеет один доверенный ключ 256 бит; это не многопользовательский IAM. Ключ передаётся Bearer в API, сравнивается по хэшу constant-time, не сохраняется в cookies/localStorage. На VDS операторский интерфейс открывается только через аутентифицированный SSH-туннель. Не проксировать его в публичный HTTPS.
- Runtime PostgreSQL login — член NOLOGIN роли delivery_api, без прямого чтения/изменения таблиц. SECURITY DEFINER wrappers с фиксированным search_path вызывают проверенные транзакции. В журнале сохраняется session_user сервиса; для нескольких операторов потребуется отдельная идентификация и аудит. Владелец схемы доверенный, без SUPERUSER в production. Не предоставлять доступ к PostgreSQL покупателям.
- Покупатель получает одноразовый токен на 30 минут. Токен — 32 случайных байта ОС, в БД только SHA-256; в URL только fragment, не HTTP-путь/параметр. Страница удаляет fragment из истории и отправляет токен в Authorization при явном нажатии. Заголовки/тела запросов с токенами никогда не логировать, включая будущий reverse proxy. Одно атомарное погашение на стороне БД до передачи файла: обрыв сети требует нового кода. Оператор может отозвать неиспользованный код и создать новый; одновременно один активный код на подписку. Выдача до активации возможна (иначе нельзя установить APK для получения installation ID). Это не активация подписки.
- Каталог текущего APK `release.json` фиксирует tag, package, versionCode/versionName, SHA-256, размер, signer SHA-256, Git revision. Это опубликованный подписанный RC1; хэш совпал при скачивании артефакта Actions. При старте сервер повторно проверяет размер, SHA-256, реальную подпись apksigner и package/version через aapt, сохраняет проверенные байты в памяти. Файл и проверяющие программы принадлежат доверенному администратору и монтируются read-only; не принимать APK и пути от клиентов. Обновление каталога только через проверенный PR.
- Общие лимиты 120 административных и 60 загрузочных запросов/мин на процесс, тело JSON максимум 4096 байт, SQL timeout 5s, HTTP handler timeout 12s. Это предварительная защита локального сервиса, не полноценный публичный rate limiter. Перед внешним доступом нужен TLS, per-source rate/concurrency и ограничения соединений на отдельном прокси, запрет логирования Authorization, контроль ёмкости и резервирование. Не обещать защиту от DoS или абсолютную защиту APK.
- Не хранит записи о долгах и платёжные данные. UUID клиентов сопоставляются с их контактами вне сервиса доверенным оператором. Платёж подтверждается вручную, без списания; сумма проверяется по тарифу, повтор того же event UUID возвращает предыдущую операцию. Не создавать другой UUID для повторной обработки одного платежа. Клиенту необходимо передать актуальную сборку; APK пока не применяет entitlement.

## API

Административный listener: GET `/`, GET `/api/v1/plans`, `/release`, `/subscriptions?after=uuid`, `/subscriptions/{id}`, `/subscriptions/{id}/history`. POST `/subscriptions`, `/subscriptions/{id}/installation`, `/grant`, `/download`, `/downloads/{event}/revoke` (все операции в пространстве /api/v1). API требует единственный Bearer токен. Нет CORS, cookies, динамического SQL или сторонних ресурсов. Ошибки не раскрывают внутренние SQL сообщения. История — последние 100 событий каждого типа; список — keyset pagination по UUID.

Публичный staging listener: GET /download, /download.js, /style.css, POST /api/v1/download (одноразовый Bearer, пустое тело). Нет административных маршрутов. Неиспользуемый, отозванный, просроченный, уже использованный, неподходящий релиз возвращают одинаковый 404; перегрузка 429/503. Персональный URL формируется из настроенного origin, не из заголовка Host.

## Локальная подготовка (отдельная БД)

CI содержит полный воспроизводимый сценарий без production-секретов. На выделенной тестовой БД PostgreSQL 17 (владелец схемы с правом CREATEROLE) последовательно применить 001 и 002, затем создать отдельный LOGIN-член delivery_api с новым защищённым паролем. В файле настройки libpq использовать локальный Unix socket либо loopback IP; сервер откажет сетевому адресу. Создать 32-байтный admin key `openssl rand -hex 32` в файле с правами 0600. Не использовать ключ APK-подписи или SSH. Секреты и путь к DB-конфигу передаются через environment **ссылками на файлы**, не коммитятся.

Переменные: DELIVERY_DB_CONFIG_FILE, DELIVERY_ADMIN_TOKEN_FILE, DELIVERY_APK, DELIVERY_APKSIGNER, DELIVERY_AAPT, DELIVERY_ADMIN_ADDR, DELIVERY_PUBLIC_ADDR, DELIVERY_PUBLIC_ORIGIN. Оба адреса только loopback и разные. Для локальной проверки 127.0.0.1:18081 / 127.0.0.1:18082, origin http://127.0.0.1:18082. Для будущего клиента origin HTTPS с согласованным доменом. Сборка `cargo build --locked` в delivery/service после фиксации Cargo.lock. Права к БД и подписанному APK проверяются при старте.

## Приёмка

- Применение миграций, прежние тесты этапа 1, privilege/expiry/revoke SQL, синтетические HTTP запросы, отрицательные сценарии, конкурирующее использование одного токена, сравнение настоящего APK с SHA-256, отказ старта с повреждённым APK и не-loopback admin.
- Браузер Selenium: вход, создание, привязка, trial, оплата, адаптивность 1280/390, выдача, фактическое скачивание и повторный отказ. Скриншоты только синтетических данных до показа ссылки. Не считать QA закрытым до чтения результатов/артефактов точной ревизии.
- Lockfile должен быть получен из первого CI и сохранён в репозитории до интеграции; прямые версии закреплены. Никакого автоматического production-deploy. Rust toolchain, зависимости, подпись, API и браузер проверяются в CI, текущая среда не содержит cargo/PostgreSQL/Docker.

## Следующий этап и ограничения

Обязательны Android entitlement Ed25519 (отдельный серверный ключ, публичный ключ в APK, проверка срока/продукта/installation ID/ревизии), безопасная активация и обновление, policy после истечения: сохранить просмотр, погашение, экспорт и восстановление. Старый офлайн-токен не отзывается мгновенно; предложить и проверить ограниченный офлайн-срок. Настроить ограниченный доступ к staging через отдельную инфраструктуру, TLS, бэкап/восстановление, отдельные roles, выдачу без утраты данных и правовую готовность. Никакие реальные продажи и изменение VDS этим PR не выполняются.

## Многопроектный каталог (требование Issue #75)

`003_projects.sql` добавляет название и уникальный Android package ID, реальные счётчики подписок и подтверждённых начислений, создание проектов и тарифов через ограниченные SQL-функции. API GET/POST /api/v1/projects, GET/POST /api/v1/projects/{code}/plans, GET /api/v1/subscriptions?product=code&after=uuid. Новый проект изначально без тарифов и без одобренной сборки; оператор явно вводит суммы. Прежние тарифы «Расчёта» сохраняются. Повтор идентичного создания безопасен, конфликт метаданных или цены отклоняется. Редактирование уже созданных тарифов потребует версионирования. Клиент может иметь по одной подписке в каждом проекте, срок и журнал изолированы по продукту; агрегаты — реальные начисления, не банковские поступления. Выдача APK другого проекта запрещена до расширения верифицированного каталога артефактов. Это backend для единой нативной Ventry Admin, не готовая Android-админка. Удалённая аутентификация и выпуск entitlement остаются отдельными этапами.

Резервная web-админка теперь использует тот же runtime-каталог, переключает область подписок и тарифов по продукту, показывает реальные счётчики и позволяет зарегистрировать проект/тариф. В браузерной приёмке создание второго проекта и отдельного тарифа, подтверждение начисления и блокировка чужого APK проверяются через настоящий API. Нативное приложение остаётся Issue #75; этот интерфейс — резервный операторский инструмент, а не его замена.
