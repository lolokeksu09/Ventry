# Ventry Delivery — отдельный закрытый контур на VDS

Не production и не публичная коммерческая выдача. Существующий Ventry сайт имеет отдельный Compose, порты 80/443 и restricted SSH entrypoint. Этот каталог не изменяет их и не использует ключ сайта. Пакет предполагает отдельный проект Docker ventry-delivery, PostgreSQL volume и каталог состояния /opt/ventry-delivery-state. Не запускайте provision повторно: повторная генерация Ed25519 seed ломает лицензии. Скрипт отказывается при существующих данных. Нельзя выполнять down -v. Перед обновлением — backup, тест миграций/восстановления, pin конкретного commit. На текущем VDS ничего автоматически не изменяется.

## Доступ с телефона

По умолчанию TLS-порты 18443/18444 опубликованы только на 127.0.0.1; внутренние Rust listeners 18081/18082 и PostgreSQL не опубликованы. Для телефона подготовить существующий приватный WireGuard интерфейс и peer владельца отдельно; передать его имя и фактический RFC1918 IPv4 в provision. Скрипты проверяют принадлежность адресу интерфейса. Не привязывать к публичному IP или 0.0.0.0. Отдельная host firewall policy должна запрещать вход на эти порты с публичного интерфейса и иных источников (Docker NAT/firewall проверяется на реальном VDS). WireGuard и firewall автоматически не меняются.

TLS с отдельным частным CA и IP SAN, SHA-256 CA сверить по независимому доверенному SSH-каналу. Ventry Admin 0.3.0 умеет импортировать публичный CA (файл ca.pem) через системный выбор документа; нормальная проверка hostname/SAN и срока остаётся. Не передавать ca-key.pem или signing-key. Адрес https://PRIVATE_IP:18443; ключ оператора читается владельцем локально из secrets/admin-token. Не публиковать ключ в чат/репозиторий/логи. Ключ только для входа, выдаётся отзываемый 15-минутный сеанс; сервер хранит хэш и монотонный deadline, максимум 8 сеансов. Restart инвалидирует сеансы. При выходе запрос отзыва; если сеть упала, сеанс истекает самостоятельно. Master по умолчанию не авторизует операции. Настройка legacy=true исключительно для прежних локальных HTTP тестов.

Customer port 18444 также приватный и allowlisted: только download/activation/entitlement, никогда admin. Настоящие покупатели не могут пользоваться этим staging, пока не настроен отдельный публичный HTTPS customer origin, общедоверенный сертификат, внешние per-source/concurrency limits и проверка лицензионного APK. Выданные здесь ссылки предназначены для закрытого теста; текущий RC не проверяет подписку.

## Запуск новой закрытой инсталляции владельцем VDS

В проверенном checkout репозитория (точный commit после CI):
```bash
cd delivery/deploy
bash provision-private.sh --state /opt/ventry-delivery-state
bash start-private.sh /opt/ventry-delivery-state
bash backup.sh /opt/ventry-delivery-state
```
Для приватного WireGuard добавить --wireguard ИМЯ_ИНТЕРФЕЙСА ЕГО_IPV4 только после настройки сети владельцем. Не угадывать IP. Требуются Docker Compose, Python 3, OpenSSL, curl, ip и wg для WireGuard. Provision создаёт state, seed, отдельные пароли БД, CA и server cert (не заменяет существующие), проверяет опубликованный APK по хэшу. Api build использует Rust locked и Ubuntu runtime apksigner/aapt; startup проверяет настоящий APK, сертификат и metadata. Docker CI обязан подтвердить именно эти runtime tools. Отдельный Caddy собран тем же patched build script, что сайт. БД/сервис/edge используют общий сетевой namespace, PostgreSQL слушает loopback. Порты контейнера 18443/18444 привязаны к конкретному частному адресу хоста. Root-only state directory with narrowly scoped read-only container mounts. Публичный CA и raw Ed25519 verification key можно экспортировать отдельно; приватный signing seed и БД backup должны храниться в защищённой резервной копии. Архив базы может содержать метаданные подписок, не передавать в public.

start-private.sh строит и запускает стек, проверяет TLS без -k, отсутствие admin routes с клиентского порта, авторизованное чтение проектов и отзыв сеанса. Если первый запуск не прошёл, сохранить state и логи, не повторять provision и не удалять volume. backup.sh создаёт pg_dump custom-format и проверяет каталог/хэш, не утверждает что восстановление проверено. CA cert expires 730d, server cert 365d; ротация TLS, backup/restore ключа и миграции последующих версий — отдельные runbook gates.

## Остаток до реальной продажи

Текущий production сайт не получает новые маршруты. Требуется доступ владельца к VDS для первого install (существующая ограниченная CI-команда принимает только сайт), настройки WireGuard/host firewall и DNS/TLS клиентского endpoint. Затем production pin и HTTPS в подписанной сборке «Расчёта», испытание обновления и переноса на реальных устройствах, восстановление БД и signing key. Не объявлять коммерческий запуск по результату CI staging.
