# Public license gateway — staged owner opt-in

Proposed canonical hostname: license.ventrylab.top (not yet verified or configured in DNS). No change to the deployed site Caddyfile, private TLS, tokens, license signature keys, APK or production database. This patch supplies a separate gateway and optional configuration, not a live publication.

Topology: public HTTPS Caddy → dedicated external Docker network ventry-delivery-public → gateway → authenticated private TLS to db:18444 on the existing Delivery default network. Only gateway is attached to both networks. Website never joins Delivery default network; DB/admin ports are not published by the gateway. The gateway has no DB credentials or signing seed. TLS trusts only the existing private CA and checks the actual private IP SAN. Public HTTPS terminates at the site Caddy using a publicly trusted certificate. Caddy overwrites X-Ventry-Client-IP with its actual socket peer IP; do not install behind another proxy/CDN without revisiting trusted-source configuration. Only these two trusted containers may join the public-ingress network. The header is not a standalone authentication mechanism.

Exact routes: GET/HEAD /download, /download.js, /style.css; POST /api/v1/download, /api/v1/activate, /api/v1/entitlement. All admin, other methods, encoded paths and query strings denied. Gateway rejects oversized bodies before upstream, strips spoofed forwarding/cookie headers, bounds source quota memory (4096 entries; 30 requests/min/source; IPv6 /64), concurrent in-flight upstream requests (16), request/header/response times. Existing global backend quotas stay in place; shared NATs may hit limits, Retry-After is a conservative fixed-window upper bound. These are application controls, not volumetric DDoS protection.

## Before owner activation
1. Verify main CI and current VDS installation. Complete schema 006 upgrade only with approved owner maintenance/backup. Keep existing keys. Verify licensed signed APK and embedded public key; the current release candidate may not enforce licenses. Do not advertise commercial delivery until the actual APK passes acceptance.
2. Configure DNS for the proposed hostname, verify public cert and firewall. Create the dedicated Docker network with owner authority; inspect existing membership first. Attach only site Caddy and gateway. The compose overrides are relative to the first compose file (run from verified repo root).
3. Review delivery/public/delivery.override.yaml and site.override.yaml. Append license.Caddyfile to the real site config only after approval. Preserve this configuration and network in the restricted site's deploy path: existing CI site release replaces the Caddyfile and uses base compose, so a manual overlay alone will NOT survive future deployments. Do not bypass the restricted SSH command. Integrate and validate persistence before enabling real customer traffic.
4. Configure DELIVERY_PUBLIC_ORIGIN using the override; no private address in newly issued links. Keep existing private admin TLS and WireGuard. Verify public GET /download and invalid POST returns generic error, admin endpoints 404, correct activation/refresh signature and exact approved APK from a disposable test subscription; verify ordinary site and private admin still work. Do not use a real customer for testing.
5. Rollback: disable public hostname/route first, restore previous API public origin/configuration; no deletion of DB, keys or volumes. Previously issued public links will need review if endpoint is unavailable.

CI runs TLS gateway tests and Compose validation. Real DNS, public certificate, full end-to-end Docker ingress, network isolation and site-deploy persistence still require verification. No live VDS action performed.
